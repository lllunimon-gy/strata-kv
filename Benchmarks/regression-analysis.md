# 性能回退复查：证据、改动与保留决定

作者：gy

## 结论

最有支持的收益是自动合批：两轮同机实验的 P50 分别降低 38.9% 和 27.1%。缓冲写的中位数也下降，但并非全部尾延迟改善。同步写、读取、重开和压缩没有一致改善，不能继续使用第一轮的好看数字代表最终结论。
读取 get/entry 拆分试验没有稳定收益，已回退。最终保留的 Sources 与第一轮候选 `13d32d7` 相同，另增加读取时钟语义回归测试。第二轮原始数据继续保留，不删除不利结果。

## 为什么原来的回退表不能直接归因

最初 v0.2 与 v0.4 是不同次 CI 的单次基准；主机状态不同、调用数少，压缩甚至只测一次。后续两轮同机对照中，v0.4 的十条同步批写 P50 均低于同轮 v0.2，因此原先“批写中位延迟明显回退”的结论没有稳定复现。
粗分段测量显示同步阶段存在较大尾延迟，且轮次间变化明显；这与 fsync/调度噪声相容，但没有 OS 层采样证据，不能断言噪声解释了全部差异，也不能把 P99 下降全归因于编码优化。
小规模压缩的结构性成本则确实增加：v0.2 阻塞重写一个文件；v0.4 先建立并发布增量段，再发布 checkpoint 清单，构建期间允许继续读写。额外文件/目录同步和清单发布不能为降低数字而直接删去。
读取还增加了 TTL 时间判定、revision/文件引用管理和锁外 pread 生命周期。旧版本没有完全相同的业务语义；单线程微小读取开销与并发时的阻塞情况应分别看。

## 实现中发现的重复开销

| 位置 | 采取的改动 | 保持的边界 |
|---|---|---|
| 普通提交反复获取索引锁 | 捕获位置/序号一次，统计与索引一并发布，普通无轮转路径两次索引锁 | 写者串行、读者只看已提交索引；文件 IO 在索引锁外 |
| 一个批次调用三次 write | 正常路径改为 writev，避免完整帧拼接副本 | 处理短写/EINTR；writev 不代表原子事务，提交尾、CRC、同步仍保留 |
| 整数字段创建临时 Data/数组，正文反复扩容 | 直接追加小端整数，提前验证并预留容量 | 磁盘字节格式不变，快慢写入路径字节一致 |
| 合批接纳时完整编码，提交又编码 | 接纳只验证和计数，不拷贝正文或计算 CRC | 提交仍验证实际 revision，非法请求和背压语义不变 |
| 已确认同步的旧段再次同步 | 跟踪活动段是否仍需同步 | buffered 写入和重开后的未知状态仍同步；清单/目录顺序不变 |
| 压缩逐 key 从 URL 提取文件名 | FileRef 缓存文件名 | 旧快照保留文件描述符的生命周期不变 |
| 打开时重复读取 manifest | 复用已经验证的 manifest | 缺清单、CRC、文件名和序列检查保留 |

这些改动组合测量，尚未做逐项消融，不能把总体变化精确分摊给每一项。保留它们的依据是明确减少重复工作、合批/缓冲路径的实测支持，以及正确性验证；不是所有指标都已变好。
未保留 get/entry 拆分试验：它减少了返回信息的组织，却没有稳定改善 get 或 entry。保留该试验新增的时钟回拨测试，避免以后为了速度跳过普通读取的时间钳制。

## 阶段剖分的限制

每批十条、每值 256 B、1,000 次同步提交，用 fault 回调记录头后、正文后、提交尾后、同步后的时间。回调路径保留三次写入，所以它不包含正常路径 writev 的收益。
encode-lock-header 包含验证、编码、锁和头写；publish 包含索引发布和返回路径。它们不是纯 CPU/锁时间，各阶段分位数也不能相加推导总分位数。
读取与重开均为热缓存。写入输入大部分预先构造，合批含排队与请求提交；不能把这些数字直接与旧单次 benchmark.json 的不同计时范围相减。

## 验证与复现

第一轮实现通过 51 项测试、12 个子进程中断场景、iOS 示例编译和 15 项 Thread Sanitizer 引擎测试；读取试验增加的测试使总数达到 52。最终提交证据见 [验证范围](../Documentation/validation.md)。
新增用例覆盖向量短写、跨缓冲区推进、EINTR、零写、注入 ENOSPC、快慢路径字节一致、UTF-8/批次容量、同步/缓冲轮转、重开后的同步以及读取时钟回拨。ENOSPC 为适配器注入，不是实际填满磁盘；未执行真机断电实验。

```sh
python3 Benchmarks/compare.py --workspace /tmp/strata-compare-new --output comparison.json --rounds 6
```

需要 macOS、完整 Git 历史、新工作目录。脚本只在独立克隆中替换 CLI 探针；所有轮次保留。Actions 的 CI → Run workflow 也会执行六轮对照，普通 push 运行正确性检查和标准基准。

## 尚未解决的性能问题

同步写和小规模压缩仍明显受文件/目录同步与主机状态影响。后续应在固定真机上记录压缩捕获、构建、发布各阶段，以及并发读写 P95/P99 和空间峰值；确认热点后再考虑合并维护请求或压缩触发策略。当前没有加入自动频繁压缩，也没有通过降低持久性换取数字。
当前对读取没有确认的性能提升，对压缩没有稳定提速结论。这些项保留为明确的后续工作，不把“已改代码”等同于“问题已解决”。
