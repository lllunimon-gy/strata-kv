# 提交、确认和恢复是三个时刻

writeBatch 先在内存编码并验证大小，再依次写 header、payload、CMIT。
同步模式在 fsync 成功后更新内存索引并返回。提交标记写完后进程退出，调用方可能没收到成功，
重开却能读到新值。这是“已提交但未确认”，上层业务重试需要考虑幂等性。

实例用 NSLock 串行化所有操作，C 层循环处理 short write、EINTR 与 pread。
fault 回调在锁内，仅用于测试，不能重入当前实例。追加开始之后发生错误会毒化实例；
重开时重放所有完整批次、截断未完成尾部，再允许写入。

内存索引保存 key → 文件偏移与长度。读取通过 pread 获取值。
压缩持有同一把锁，按 key 排序读出有效值，分批写入 store.compacting，fsync 后 rename。
rename 前退出仍选择旧日志；rename 后退出选择新日志。重开清理残留临时文件。
不允许其他代码改写日志；校验在恢复时执行，get 不对外部运行时篡改提供完整检测。

恢复阶段读取完整 Data，简单但不适合超大日志。下一步可以做流式帧解析，并限制单帧缓冲。
压缩是 stop-the-world，不宣称低延迟后台压缩。要做后台压缩，必须解决快照和新写入的归并问题。

对同步语义和硬件假设的阅读：https://www.sqlite.org/atomiccommit.html
SQLite 的保证不能直接套用到本实现；这里没有实现其完整文件系统协议。
